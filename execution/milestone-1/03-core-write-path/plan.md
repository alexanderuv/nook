# Core write path — Plan

A note on references: this plan leans on two earlier documents in this folder.
[Spec-1](./spec-1.md) numbers the behavior it pins — REQ for requirements, EDGE
for edge cases, AC for acceptance criteria. [The discovery](./discovery.md)
numbers its findings FIND and its open questions Q. When this plan cites one of
those codes it is pointing at a numbered entry in those documents, and it states
the point in plain words alongside the citation — the pointer is a cross-check,
not required reading.

## Analysis

What already exists, checked against the repository rather than remembered:

- **The database schema and its test harness, built by epic 02.** The file
  `core-service/src/main/kotlin/io/nook/core/db/Tables.kt` describes all six
  database tables in Kotlin using Exposed, the Kotlin library this project uses
  to talk to SQL databases. A drift-guard test — a test that fails the build if
  those Kotlin descriptions ever stop matching the real database — keeps the two
  in step. `Migrations.kt` applies the database's versioned change history (the
  Liquibase changelog under `db/changelog/`) from inside the running process.
  For tests, `EmbeddedPostgresSupport.freshMigratedDatabase()` starts a real
  PostgreSQL server inside the test process and hands each test class a freshly
  migrated database, so tests run against the real thing rather than a stand-in.
  Eleven permanent tests probing schema behavior are already in place, and CI
  runs `./gradlew check` on Linux. None of this changes: this epic builds on top
  of that foundation, not into it.

- **The module layout.** The `:core-service` module already depends on
  `:contract`, the module meant to hold the types both sides of a future API
  will share. Today `:contract` holds only a placeholder file
  (`Placeholder.kt`) and the kotlinx-serialization build plugin. A build check
  named `nook.persistence-boundary` guards it: nothing in `:contract` may
  depend on database code, so the types added there in this epic must be plain
  Kotlin with no database imports. `Main.kt` in `:core-service` is also a
  placeholder and stays one — in this epic, the only caller of the new code is
  test code running in the same process.

- **The enum code maps.** Fields such as an item's type and status are stored
  in the database as small integers, not words — a project-wide convention. The
  header of the first changelog file documents which number means what: item
  type is 1 = epic, 2 = task, 3 = bug, 4 = chore; item status is 1 = todo,
  2 = in progress, 3 = done, 4 = cancelled; release status is 1 = planned,
  2 = in progress, 3 = released, 4 = cancelled. This epic turns those maps into
  application enums carrying the same numbers. Row identifiers (UUIDs) are
  generated by the application, not the database.

- **The database's own safety rules.** The schema already enforces several
  rules by itself, through named constraints — rules the database checks on
  every write no matter what the application does. The discovery proved
  (finding FIND1) that when one of these fires, the error reaches application
  code carrying the constraint's name and its standard SQL error code, so the
  application can translate it into a meaningful error. The names, all present
  in `Tables.kt`: `uq_project_slug`, `uq_item_project_slug`, and
  `uq_release_project_slug` each enforce that a slug is unique in its scope;
  `fk_item_parent_same_project`, `fk_item_release_same_project`, `fk_dep_item`,
  and `fk_dep_blocker` each enforce that a reference points at a real row in
  the right project; `pk_item_dependency` forbids duplicate dependency rows;
  and `ck_dep_no_self_block` forbids an item from blocking itself.

What this epic builds was decided elsewhere; this plan links rather than
restates:

- **[Spec-1](./spec-1.md)** is the behavior contract this plan builds to: the
  seven write operations, how references are resolved, how slugs work, the
  status and type-change rules, blockers, releases, and what must hold when two
  writers act at once — pinned as 40 requirements, 15 edge cases, and 25
  acceptance criteria. The test suite below is that contract, executed.

- **[The discovery](./discovery.md)** settled the mechanisms by running
  experiments against the real database stack. Adopted from its
  recommendation:
  - Every write starts by taking a per-project advisory lock (FIND7). An
    advisory lock is a PostgreSQL feature — reached here through
    `pg_advisory_xact_lock` — where the application asks the database to hold
    a lock on a number of the application's choosing, released automatically
    when the transaction ends. With every write to a project taking that
    project's lock first, two writers to the same project take turns instead
    of interleaving.
  - The cycle check — does this new "blocked by" edge create a loop? — runs as
    a walk over the dependency edges in application code, inside the locked
    transaction (FIND4).
  - Database constraint errors are translated by constraint name into
    structured application errors (FIND1).
  - Every write transaction sets `maxAttempts = 1`, because Exposed's default
    is to silently re-run a failed transaction block up to three times —
    behavior this plan wants visible, never silent (FIND3).

  The discovery also ruled things out; do not re-investigate them: checking
  first and then inserting, without a lock, still lets two simultaneous
  writers store a real cycle (FIND5); PostgreSQL's SERIALIZABLE isolation
  level is correct but forces retry handling that the lock avoids (FIND6);
  retrying inside the same transaction after a constraint violation cannot
  work because the transaction is already dead at that point (FIND2); and
  doing the cycle check in recursive SQL is correct but slower, and Exposed
  misreports its result unless the statement type is spelled out (FIND4).

- **[PRD-1](../prd-1.md)** frames the epic: its requirement REQ3 asks for a
  single write path enforcing spec 04's semantics; its goal GOAL3 wants every
  settled rule mapped to a named test; its goal GOAL4 keeps persistence inside
  `:core-service`.

Constraints that bound the change: the changelog needs no new entries — every
database-side rule this epic leans on is already in the schema. The
`created_by` and `updated_by` columns keep their `system` defaults, because
plumbing a real actor through is epic 08. Reads, network exposure, and
adapters are later epics — the write path's public surface is exactly the
seven operations spec-1 names in its REQ1.

## Approach

Build the write path in `:core-service` on the epic 02 foundation, with the
shared shapes in `:contract`:

- **Contract types.** `:contract` gains its first real code: three enums —
  `ItemType`, `ItemStatus`, `ReleaseStatus` — each member carrying its integer
  from the changelog map, written out explicitly; three data classes (Kotlin
  classes that just hold values) — `Project`, `ProjectItem` (one class covers
  all four item types), and `Release`; and the error surface — an `ErrorCode`
  enum with four members (`validation_failed`, `not_found`, `conflict`,
  `cycle`), a class holding a structured error, and the exception that carries
  it. These stay plain classes: preparing them for the wire is epic 05's
  concern. (Found in execution: entity ids use Kotlin's own `kotlin.uuid.Uuid`
  type, not Java's `java.util.UUID` — the database layer's column type is the
  Kotlin one, and carrying a single id type end to end beats converting at
  every boundary.)

- **One write-service class** in `:core-service` as the single entry point,
  exposing exactly the seven operations. Every operation follows the same
  shape: open one fresh Exposed transaction with `maxAttempts = 1`; take the
  advisory lock; resolve the caller's references (a value that parses as a
  UUID is looked up as an id, anything else as a slug within the target
  project); validate against spec-1's rules; make the change through Exposed;
  map the resulting row to its contract class and return it. Any failure
  throws the structured-error exception, which also aborts the transaction —
  so a failed operation leaves no partial change behind, which is exactly the
  no-partial-effect rule spec-1's REQ6 demands, at no extra cost.

- **Locking.** Every write scoped to a project locks on that project's id.
  `create_project` is the one exception: there is no project yet, and project
  slugs must be unique across the whole instance, so it locks on a single
  fixed instance-wide key instead. Same mechanism, two scopes.

- **Slugs.** A slug is the short human-readable identifier a project or item
  carries, like `user-login-flow`. Deriving a slug from a name and validating
  an explicitly supplied slug are pure functions — code that takes input and
  returns output without touching a database. When a derived slug is already
  taken, the allocator lists the slugs in use in that scope and appends the
  first free number (`user-login-flow-2`); that scan is safe because it runs
  under the lock. The database's unique constraints stay on as a second line
  of defense, translated to a `conflict` error if they ever fire.

- **Cycle detection.** A "blocked by" edge must never create a loop — item A
  blocked by B while B is blocked by A would mean neither can ever become
  ready. The check is a depth-first walk over the project's dependency edges,
  with the target item's current edges swapped for the newly supplied set, run
  inside the locked transaction. If the item can be reached from any of its
  would-be blockers, the operation is rejected with the `cycle` error.

- **Error translation.** A small map from constraint name to error code sits
  behind the application-level validation as a backstop — the safety net for
  anything validation misses: uniqueness constraint names translate to
  `conflict`; foreign-key and CHECK constraint names to `validation_failed`.
  The `cycle` code only ever comes from the walk — no constraint produces it.

Why this way over the obvious alternative: there is no live alternative left —
the discovery raced the candidates against the real stack, and the advisory
lock won on every axis (no failures to catch, no retries to write, and it
closes the slug race as a side effect). The rest of the shape follows spec-1
directly.

Unverified assumption, named: the lock-and-transaction discipline has only run
as throwaway experiment code, never as module code. So the scaffold lands
first, and the two concurrency stress tests (spec-1's AC23 and AC24) run as
early as each has enough operations to exercise — not at the end.

Blast radius — what this change touches: `:contract` main sources (their first
real code) and its tests, and `:core-service` main and test sources. (Found in
execution: also one scope change in `core-service/build.gradle.kts` — the
PostgreSQL driver moves from runtime-only to compile-visible, because the
error translator reads the violated constraint's name off the driver's
exception type. No new dependency; the version catalog is untouched.) What it
must leave untouched: `db/changelog/`, `gradle/libs.versions.toml` (no new
dependencies), `:mcp-server`, `:web-app`, `build-logic/`, epic 02's tests and
drift guard, `Main.kt`, and `docs/`.

## Steps

- [x] **STEP1** — Define the contract types in `:contract` (package
  `io.nook.contract`): the three enums with their explicit integer codes, the
  three entity data classes, `ErrorCode`, the structured-error class, and its
  exception; verify: a `:contract` unit test asserts that every enum member's
  integer equals the one documented in the changelog header, and
  `./gradlew :contract:check` runs green — which includes the
  persistence-boundary check.

- [x] **STEP2** — Write the slug functions in `:core-service` as pure code:
  derivation — lowercase the name, collapse every run of characters outside
  a–z and 0–9 into a single hyphen, trim hyphens from the ends (REQ19) — and
  explicit-slug validation — non-empty; only a–z, 0–9, and hyphens; and not
  shaped like a UUID, so a slug can never be mistaken for an id (REQ22);
  verify: table-driven unit tests — one test body run over a list of
  input/expected pairs — cover the derivation and validation rules (REQ19,
  REQ21, REQ22) and the edge cases for empty, symbol-only, and UUID-shaped
  names (EDGE1, EDGE4, EDGE5), with no database involved.

- [x] **STEP3** — Build the write-path scaffold in package
  `io.nook.core.write`: the write-transaction helper, which opens a fresh
  transaction with `maxAttempts = 1` and takes the advisory lock — on the
  project's id, or on the fixed instance key; the reference resolver, which
  looks a value up as an id if it parses as a UUID, otherwise as a slug
  within the target project, and fails with `not_found` if neither finds a
  row (REQ3, REQ4); the mapping between enum members and their stored
  integers; and the constraint-name-to-error-code translator; verify: an
  integration test proves the lock makes writers take turns — two threads
  write to one project with a synchronization barrier between them, and the
  test shows the second thread waits until the first commits — plus resolver
  tests covering the id case, the slug case, and the not-found case, and a
  test asserting the translator has an entry for every constraint name
  declared in `Tables.kt`. (Found in execution: enumerating CHECK-constraint
  names through the table declarations requires a live SQL dialect, so that
  test runs its enumeration inside a transaction on the embedded test
  database rather than as a pure no-database test.)

- [x] **STEP4** — Implement `create_project`: takes the instance-wide lock,
  applies the slug rules with the whole instance as the uniqueness scope,
  leaves the artifact-repository URL unset, and sets no status — projects
  don't have one (REQ8, REQ9); returns the full `Project`; verify: the named
  tests for the project half of AC2, and for AC3, pass.

- [x] **STEP5** — Implement `create_item`: validates the item type, enforces
  containment — which item types may nest under which (REQ10 through REQ14) —
  sets the initial status to todo, allocates the slug with the
  first-free-number rule, and translates any constraint violation on insert;
  verify: the named tests for AC4 through AC8 and AC10 pass.

- [x] **STEP6** — Stress the slug allocation (AC24): two callers concurrently
  create an identically named item in the same project, repeated 100 times;
  verify: every repetition ends with two successes carrying different slugs.
  This is the earliest proof that the lock discipline holds in real module
  code, which is why it runs now rather than at the end.

- [x] **STEP7** — Implement `update_item`: partial update, meaning only the
  supplied fields change (REQ16); the slug stays the same unless explicitly
  changed (REQ17, REQ23, EDGE3); moving an item under a new parent (REQ18);
  the status vocabulary (REQ25 through REQ27); the rules for changing an
  item's type (REQ28 through REQ30); and the updates that change nothing
  (EDGE7, EDGE8); verify: the named tests for AC11 through AC17 and AC25
  pass. (Folded in during execution: AC9 — the explicit-slug conflict on
  create and the own-slug no-op on update — lands here too, since its second
  half needs `update_item`; no earlier step had claimed it.)

- [x] **STEP8** — Implement `set_item_blocked_by`: the supplied set replaces
  the whole existing set, duplicates removed (REQ31, REQ34); every blocker
  must live in the same project and no item may block itself (REQ32); and the
  cycle walk rejects loops (REQ33). Then stress the cycle check (AC23): two
  callers concurrently add the two halves of what would become a loop,
  repeated 100 times; verify: unit tests run the walk, without a database,
  over the three shapes the discovery used — a chain, a diamond, and an edge
  that looks dangerous but isn't — the named tests for AC18 through AC20
  pass, and every stress repetition produces exactly one `cycle` rejection
  and never a stored loop.

- [x] **STEP9** — Implement `create_release`, `update_release`, and
  `assign_epic_to_release` (REQ35 through REQ38, EDGE11, EDGE12), with
  release slugs unique per project rather than per instance; verify: the
  named tests for AC21 and AC22 pass.

- [x] **STEP10** — Close the surface: a test asserts the write service's
  public operations are exactly the seven — in particular, no delete anywhere
  (AC1); run `./gradlew check` on a clean checkout, then push for the CI run;
  verify: check green locally and in CI, with the new tests visibly executed.

## Caveats & rabbit holes

- **no-go: read operations** — `get_item`, `list_items`, and
  `get_ready_items` belong to epic 04, and "just a little getter" is how they
  leak in early; instead: when a test needs to inspect state, it queries the
  tables directly through Exposed in test code — the service's public surface
  stays the seven mutations.

- **no-go: exposing the service** — no web routes, no remote calls, no MCP;
  instead: `Main.kt` stays a placeholder, and the in-process test caller is
  the only caller until epic 05.

- **no-go: actor plumbing** — no `createdBy` or `updatedBy` parameters on any
  operation; instead: those columns keep their `system` defaults; epic 08
  owns that seam.

- **no-go: `update_project` and any hard delete** — neither is in the
  milestone 1 operation catalog (spec-1 REQ1, REQ2); instead: if something
  appears to need one, that is a question for the spec, not a quiet addition
  to the code.

- **caveat: the document tables exist but are off-limits** — `document` and
  `document_sequence` belong to milestone 2; instead: the write path never
  touches them, and no document rules get sketched in ahead of time. (Found
  in execution: the constraint-name translator does carry entries for the
  document tables' constraint names, because its coverage test enumerates
  every declared table. Those entries are inert backstop lookups, not
  document rules — no operation writes those tables.)

- **rabbit-hole: making the contract types serializable** — `:contract`
  already applies the serialization plugin, which invites adding
  `@Serializable` and custom UUID and timestamp serializers now; instead:
  plain data classes — the wire format gets designed when a wire exists
  (epic 05).

- **rabbit-hole: a repository layer** — an extra layer of data-access classes
  between the service and the database; seven operations in one service don't
  justify one; instead: the service uses Exposed directly, and epic 04 can
  revisit if the read side turns out to want shared queries.

- **caveat: transaction discipline is explicit everywhere** — Exposed's
  default silently re-runs a failed transaction block up to three times
  (FIND3); instead: every write-path transaction sets `maxAttempts = 1`, and
  any retry is a deliberate fresh transaction, visible in the code.

- **rabbit-hole: load-testing the advisory lock** — how the lock behaves
  under real multi-agent write volume is the discovery's open question Q5,
  and no such load exists yet; instead: leave Q5 open on the discovery — this
  epic proves the mechanism correct, not cheap.

- **caveat: epic 02's ground stays untouched** — the changelog, the table
  declarations, the drift guard's filter, and the eleven behavior tests are
  finished work; instead: any schema itch becomes a new changeset in the epic
  that needs it — and none is expected here, since every database-side rule
  this epic leans on is already in place.

## Test plan

- **TEST1** — unit: slug derivation and explicit-slug validation,
  table-driven over the slug rules (REQ19 through REQ22) and their edge cases
  (EDGE1, EDGE4, EDGE5); no database.

- **TEST2** — unit: the cycle walk over the discovery's three shapes — a
  chain, a diamond, and an edge that looks dangerous but isn't — plus the
  replace-the-whole-set semantics; no database.

- **TEST3** — every enum member's integer matches the changelog map (a pure
  unit test), and the constraint-name translator covers every constraint name
  in `Tables.kt` with the agreed error code (its enumeration runs inside a
  transaction on the embedded database — see the STEP3 note).

- **TEST4** — integration: all 25 acceptance criteria of spec-1 as named
  tests against the embedded PostgreSQL, each test named after the criterion
  it executes — the rule-to-test mapping PRD-1's GOAL3 asks for, delivered
  for this epic.

- **TEST5** — integration: the two concurrency stress tests — the cycle race
  (AC23) and the slug race (AC24) — at 100 repetitions each, green on every
  run.

- **TEST6** — build: `./gradlew check` green on a clean checkout; the
  persistence-boundary check still green everywhere, with `:contract` holding
  its new types and no database dependency.
